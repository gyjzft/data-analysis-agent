# 改动记录（CHANGELOG）

## v1.3 — 2026-08-19：沙箱主导建模 + 动态预测面板

### 背景
代码生成模式下，LLM 写的建模代码跑完就丢，模型无法保存复用；
旧工具模式虽能保存，但 DeepSeek 函数调用不稳定。两者取长补短。

### 改动内容

| 文件 | 改动 | 说明 |
|------|------|------|
| `src/tools/modeling.py` | **新增** | 沙箱主导建模模块，固定但自适应的建模流程 |
| `src/agent/core.py` | 修改 | 识别"建模请求"标记，路由到 modeling.py，不走代码生成 |
| `src/ui/app.py` | 修改 | 预测面板改为：加载模型 → 动态生成特征输入框 → 预测 |

### 沙箱主导建模（modeling.py）
- 自动识别特征列（数值 + 类别，自动排除高基数列如 name）
- `ColumnTransformer` 打包完整预处理：缺失值填充 + 标准化 + 独热编码
- 训练 4 个模型对比，选最优
- 完整保存：model + preprocessor + label_encoder + meta.json
- `predict_from_values()`：加载模型后对任意输入值预测

**核心优势**：保存的是"完整预处理流程"，预测时 transform 逻辑和训练完全一致，
不再有"get_dummies 列对不上"的问题。保存可靠性 ~100%，不依赖 LLM 写代码。

### 动态预测面板
1. 输入模型ID → 点击「加载模型」
2. 系统读取 meta.json，自动显示 20 个槽位中对应的输入框
   （数值特征→数字框，类别特征→下拉框，标签=特征名）
3. 填写后点击「预测」→ 显示结果
4. 「关闭预测」→ 面板收起，不自动消失

### 测试结果
- 回归建模（预测 salary）+ 完整保存 ✅
- 分类建模（预测 left_company）+ 完整保存 ✅
- 加载模型 → 自动识别 8 个特征（5数值+3类别）✅
- 填写特征值 → 预测输出 ✅

## v1.2.2 — 2026-08-18：聊天消息格式自检，错误不再盖住聊天

### 问题
当聊天消息格式有问题时，Gradio 会在页面中间弹出错误条，盖住聊天内容。

### 修复
`src/ui/app.py` 新增 `_sanitize_history()`：返回前用 Gradio 自己的校验器
验证每条消息，格式非法的消息自动降级为纯文本（保留文字部分）。
这样错误变成聊天里的一行文字，而不是挡住整个界面。

### 验证
- 正常消息（含图片 path）：原样通过 ✅
- 非法格式消息：降级为纯文本 ✅
- 完整对话（画图 + 纯文字两轮）：Gradio 接受整个历史 ✅

## v1.2.1 — 2026-08-18：修复图片显示格式

### 问题
Gradio 6.20.0 的 Chatbot 组件不认 `{"type": "image", "image": ...}` 格式，
显示图片时报 `ValueError: Invalid message for Chatbot component`。

### 修复
`src/ui/app.py` 中图片内容块改为 `{"path": "图片绝对路径"}`。
Gradio 会自动识别 mime 类型并内联渲染图片。

### 验证
- `_postprocess` 直接测试：path 格式通过 ✅
- 完整 handle_chat 流程：文字 + 图片内容块均被 Gradio 接受 ✅

## v1.2 — 2026-08-18：聊天体验改进

### 改动内容

| 文件 | 改动 | 说明 |
|------|------|------|
| `src/ui/app.py` | 修改 | 图片改用 Gradio 6.x 原生内容块显示（文字+图片分块） |

### 改进点

1. **图片正常显示**：assistant 消息从"文字里嵌 Markdown 图片"改为内容块格式

3. **代码出错自动修复**：执行失败时把错误反馈给 LLM，自动重试修复（最多 2 次）
4. **错误友好提示**：重试仍失败时显示友好提示，不再把原始代码抛给用户

### 验证结果

- "你好" → 纯文字自我介绍，不生成代码 ✅
- "画一个薪水的直方图" → 生成图片 + 解读 ✅
- 强制执行失败 → 自动重试后友好提示 ✅

## v1.1 — 2026-08-18：Agent 核心改为"代码生成"架构

### 背景
DeepSeek 的 OpenAI 兼容接口对自定义函数调用（Function Calling）支持不可靠：
模型经常绕过我们注册的工具，改用自己内置的 `execute_code` 工具，
并且由于拿不到真实数据，会**编造统计数字**（例如硬编码平均值）。

### 改动内容

| 文件 | 改动 | 说明 |
|------|------|------|
| `src/agent/core.py` | **核心重写** | 从"函数调用循环"改为"代码生成循环" |
| `src/ui/app.py` | 修改 | 聊天记录格式适配 Gradio 6.x；`handle_chat` 重写 |
| `src/llm/client.py` | 基本未动 | 工具解析逻辑保留但不参与主流程 |
| `src/tools/*` | 未动 | 15 个工具保留，仅"预测"功能仍在使用 |
| `tests/test_tools.py` | 未动 | 仍直接测试 15 个工具 |

### 新流程（代码生成）

```
用户提问
  ↓
LLM 生成 Python 代码（使用真实加载的 df）
  ↓
本地沙箱执行代码，得到真实计算结果 + 图片
  ↓
把真实结果交给 LLM，生成中文解读
```

### 旧流程（函数调用，已停用但保留）

```
用户提问
  ↓
LLM 从 15 个工具里选一个（如 describe_data）
  ↓
本地执行工具函数，返回结果
  ↓
LLM 写解读
```

### 为什么保留旧代码

- `src/tools/*` 的工具架构、BaseTool 抽象、注册中心是良好的设计模式学习素材
- 将来换用正确支持函数调用的模型（如 OpenAI GPT）时，可以随时切回旧流程
- 界面"模型预测"功能目前仍依赖 `ToolRegistry` 和 `predict` 工具

### 关键代码位置

| 功能 | 位置 |
|------|------|
| 系统提示词（告诉 LLM 怎么写代码） | `core.py` 顶部 `SYSTEM_PROMPT` |
| 提取代码 | `core.py` `_extract_code()` |
| 沙箱执行 + 图片捕获 | `core.py` `_execute_code()` |
| 聊天主循环 | `core.py` `chat()` |
| 预测功能（仍用工具） | `app.py` `handle_predict()` |
